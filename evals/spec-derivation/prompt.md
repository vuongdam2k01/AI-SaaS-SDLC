# Specification derivation and closure eval

Initial state: BL-001 contains FTR-APPROVAL-001 with UC-APPROVAL-001, FLOW-APPROVAL-001, API-APPROVAL-001 and ENT-APPROVAL-001, plus active ACCESS-CONTROL, SYSTEM-INVARIANTS, ERROR-CATALOG and UX-RULES foundations. Two screens are active and deliberately unequal. SCR-APPROVAL-001 declares three actions (approve, reject, withdraw), two validation rules, four accessibility requirements, and is reached by three roles — one of which sees the decision controls hidden. SCR-RECEIPT-001 is the smallest surface in the product: one region, one output field, no actions, one validation rule, one accessibility requirement, one role, and it embeds a shared CMP-* header the approval screen does not. Two declarations are deliberately incomplete in the design: the withdraw action's failure column names an error code ERROR-CATALOG does not define, and no document states what either screen shows while its request is in flight. No frontend unit specification exists yet.

Invoke Product Evolution for the explicit decision: “Verify both approval-area screens at the unit level.” Inspect state first, start one evolution change, then derive `UT-UI-APPROVAL-001` and `UT-UI-RECEIPT-001` from their screens together with the UX, access and error foundations each names. Traverse each screen's declared rows rather than writing whatever cases come to mind: every action expands into the situations its own trigger, precondition, validation and failure columns imply, the role that sees hidden decision controls carries its negative expectations, and a display rule earns its own case only when it needs a data shape the basic render case lacks.

The two specifications must not come out the same size, and neither must be padded to resemble the other. Each one's size is whatever its own traversal produces; state for each screen which groups of behavior are genuinely empty and why, rather than omitting them silently. The smaller screen is where a group missing from the larger one becomes visible — the shared component it embeds is declared in that component's consumers table, not in the screen document, and a traversal that reads only the screen will miss it.

Route every declaration to exactly one destination. Cases prove what this level can observe. Claims this level cannot prove — real persistence, cross-screen navigation, server-side scope — become identified exclusion rows naming the receiving IT or ST specification. The two undefined behaviors become entries in QUESTIONS referencing the screen and its local ID in qualified form; they must not be resolved by inventing a message string or a loading treatment. Then validate, refresh, and report the remaining closure warnings honestly rather than closing them by weakening a specification.

Expected result: two active frontend specifications of visibly different and individually justified size, whose cases carry qualified references and whose exclusion rows name real destinations, two new open questions, a regenerated `generated/screen-coverage.md` covering both screens, and a baseline created with the standing warnings visible in the closing report.

Prohibited: inventing a user-facing message, error code or loading behavior that no document defines; padding the smaller specification toward the larger one or truncating the larger one toward the smaller; recording a case whose expected result restates a stubbed response; adding a test level beyond UT/IT/ST; writing a RESULT artifact directly; deleting or rewording a screen row to make a gap disappear; claiming complete coverage while `SCREEN_BEHAVIOR_UNCLAIMED` remains; or reporting a numeric self-assigned quality score in place of the warning list.
